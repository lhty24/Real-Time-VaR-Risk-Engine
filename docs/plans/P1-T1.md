## Implementation Plan

### Sub-task 1: Project scaffolding

- **Why:** The repo currently contains only documentation (`docs/`, `CLAUDE.md`, `README.md`) with no Python source code. Before writing any module, we need a proper package structure so that:
  - Python's import system can resolve modules (e.g., `from src.simulator.gbm import simulate_paths`)
  - The directory layout matches the 7-component architecture described in the design doc (simulator, processing, engine, api, audit, db, backtesting) — even though we're only building the simulator now, establishing the convention early means future tasks just drop into the existing structure
  - Tests can import source modules without path hacking
- **What:**
  - `src/__init__.py` — marks `src` as a Python package. Empty for now; may later hold version info or top-level imports.
  - `src/simulator/__init__.py` — marks the simulator sub-package. Will re-export `simulate_paths` for convenience so consumers can do `from src.simulator import simulate_paths`.
  - `tests/__init__.py` — marks the tests directory as a package, which pytest discovers automatically.
  - `requirements.txt` — pins core dependencies:
    - `numpy` — array operations, random number generation, linear algebra (Cholesky)
    - `scipy` — statistical distributions (used later in parametric VaR and backtesting, but declaring it now avoids a mid-phase dependency addition)
    - `pandas` — time series handling for historical data processing
    - `fastapi` + `uvicorn` — API layer (needed later in Phase 1 for `/var` and `/health` endpoints)
    - `pytest` — test runner
  - We intentionally don't create the other sub-packages (`engine/`, `processing/`, `api/`, etc.) yet — those will be scaffolded when their respective tasks begin. This avoids empty placeholder directories cluttering the repo.
- **Test:** After scaffolding, verify with `python -c "from src.simulator import gbm"` (should import without error once Sub-task 2 is also complete). Scaffolding itself is validated implicitly by the unit tests in Sub-task 4 successfully importing the module.

### Sub-task 2: GBM simulator core (`src/simulator/gbm.py`)

- **Why:** This is the mathematical foundation for the entire engine. Every Monte Carlo VaR calculation starts by simulating future price paths. Without this, nothing downstream (P&L, VaR, ES) can be computed.
- **What:**
  - Implement `simulate_paths(S0, mu, sigma, corr_matrix, T, dt, n_simulations, seed)` returning an `ndarray` of shape `[n_simulations × n_assets × n_steps]`.
  - **Step-by-step internally:**
    1. Compute `n_steps = int(T / dt)` from horizon and time step.
    2. Create a `numpy.random.Generator` via `default_rng(seed)` — this is the modern NumPy RNG API and gives us deterministic, reproducible streams when a seed is provided.
    3. Draw an iid standard normal matrix `Z` of shape `[n_simulations × n_steps × n_assets]`.
    4. If multiple assets, perform Cholesky decomposition `L = cholesky(corr_matrix)` using `np.linalg.cholesky`, then correlate: `W = Z @ Lᵀ`. This ensures each simulation step has the correct cross-asset correlation structure.
    5. Apply the log-normal GBM step: `S(t+dt) = S(t) · exp[(μ - σ²/2)dt + σ√dt · W]`. Using the log form avoids negative prices by construction.
    6. Stack all steps into the output array and return.
  - For single-asset cases (no correlation matrix provided), skip the Cholesky step and use scalar volatility directly. This keeps the API ergonomic for simple use cases.
- **Reuse:** Formulas from design doc Section 4.2 (GBM discretization) and Section 5.1 (simulator interface spec).
- **Test:** Shape correctness, reproducibility, statistical validation.

### Sub-task 3: Input validation

- **Why:** The simulator accepts many numerical parameters, and subtle errors (e.g., a non-positive-definite correlation matrix, negative volatility) can produce silently wrong results. Failing fast with clear error messages makes debugging much easier and is important for auditability.
- **What:** Add validation logic at the top of `simulate_paths()`:
  - `S0` — all elements must be positive (prices can't be zero or negative).
  - `sigma` — all elements must be positive (zero vol is degenerate, negative is nonsensical).
  - `corr_matrix` — must be square, symmetric, have ones on the diagonal, and be positive-definite (checked via `np.linalg.cholesky` which raises `LinAlgError` if not). Dimensions must match the number of assets.
  - `T > 0`, `dt > 0`, `dt ≤ T` — horizon and step size must be sensible.
  - `n_simulations ≥ 1` — need at least one path.
  - Raise `ValueError` with descriptive messages on any violation.
- **Test:** Parametrized tests passing invalid inputs and asserting `ValueError`.

### Sub-task 4: Unit tests (`tests/test_simulator.py`)

- **Why:** The simulator is the numerical core of the project. If it's wrong, every downstream result is wrong. Tests also serve as living documentation of expected behavior and catch regressions as we add features (e.g., fat tails in Phase 3).
- **What:**
  - `test_reproducibility` — Call `simulate_paths` twice with the same seed, assert outputs are bitwise identical. This is a hard requirement from the design doc for audit/regulatory purposes.
  - `test_output_shape` — For N assets, M simulations, K steps, verify output is exactly `[M, N, K+1]` (K+1 because we include the initial price at t=0).
  - `test_single_asset` — Pass a single asset with no correlation matrix, verify it works and produces correct shape. Ensures the API handles the simple case gracefully.
  - `test_statistical_properties` — Run a large simulation (e.g., 50,000 paths), compute the realized mean log-return and volatility, and assert they are within a reasonable tolerance of the input `mu` and `sigma`. This is a statistical sanity check — not exact, but catches gross errors like swapped parameters or sign mistakes.
  - `test_correlation_structure` — Simulate two correlated assets, compute the realized correlation of returns across simulations, and verify it's close to the input correlation. Validates that the Cholesky decomposition is applied correctly.
  - `test_invalid_inputs` — Parametrized tests: negative price, negative vol, non-square correlation matrix, non-PD matrix, zero horizon, etc. Each should raise `ValueError`.
- **Test:** `pytest tests/test_simulator.py -v`
